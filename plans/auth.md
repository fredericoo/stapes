# Authentication

Better Auth on D1, schema authored in Drizzle, migrations applied by Wrangler.
Two roles, `admin` and `user`. The world is login-only; the editor is admin-only.

## Decisions taken

- **No guests.** `/online` redirects to `/login` without a session. The anonymous
  `stapes_uid` cookie is deleted outright — the actor id becomes the Better Auth
  user id, so there is exactly one notion of who somebody is.
- **Email + password.** No SSO, no username plugin.
- **Name tags stay derived.** `displayNameFor` keeps deriving six characters from
  the actor id; it now derives them from a user id rather than a random uuid.
  Real names are a separate change.
- **The editor is gated too.** `/map`, `/tiles` and `/voxel` write to R2 and are
  currently open to anyone who can reach the deployed URL — a larger hole than
  the game socket.
- **Roles are `admin` and `user`**, which is exactly what Better Auth's `admin`
  plugin ships by default. `rincofrederico@gmail.com` is admin.

## The instance

Bindings do not exist in a Worker's module scope, so the instance is built on
first use and kept for the isolate's life rather than rebuilt per request:

```ts
// app/lib/auth.server.ts
import { env } from "cloudflare:workers";
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "@better-auth/drizzle-adapter";
import { drizzle } from "drizzle-orm/d1";
import { admin } from "better-auth/plugins";
import * as schema from "./db/schema";

let instance: ReturnType<typeof create> | null = null;

function create() {
  return betterAuth({
    database: drizzleAdapter(drizzle(env.DB, { schema }), {
      provider: "sqlite",
      schema,
    }),
    secret: env.BETTER_AUTH_SECRET,
    emailAndPassword: { enabled: true },
    // The default limiter is per-isolate memory, which on Workers means a
    // password guesser gets a fresh allowance every time they land on a cold
    // isolate. D1 is the only shared counter available here.
    rateLimit: { storage: "database" },
    plugins: [admin()],
    databaseHooks: {
      user: {
        create: {
          before: async (user) => ({
            data: {
              ...user,
              role: user.email === env.ADMIN_EMAIL ? "admin" : "user",
            },
          }),
        },
      },
    },
  });
}

export function auth() {
  return (instance ??= create());
}
```

`admin()` adds `role`, `banned`, `banReason`, `banExpires` to `user` and
`impersonatedBy` to `session`, and treats `role === "admin"` as full control. No
custom access control needed for two roles.

### Route guards

```ts
export async function requireUser(request: Request) {
  const session = await auth().api.getSession({ headers: request.headers });
  if (!session) throw redirect(`/login?next=${encodeURIComponent(new URL(request.url).pathname)}`);
  return session.user;
}

export async function requireAdmin(request: Request) {
  const user = await requireUser(request);
  if (user.role !== "admin") throw new Response("Not found", { status: 404 });
  return user;
}
```

404 rather than 403 on the editor routes, so a signed-in player probing `/map`
learns nothing about what is there.

Applied to: `map` loader+action, `tiles` loader+action, `voxel` action, `play`
loader (`requireAdmin`); `online` loader (`requireUser`). `tilesets/:file` stays
open — it serves the PNGs the world needs to draw.

### Nav

Players see one route, so the header must not advertise the others. A root
loader returns `{ user: { id, role } | null }`; `AppShell` reads it with
`useRouteLoaderData("root")` and renders the editor links only for `admin`. The
guards are the enforcement — hiding the links is only so the UI does not lie.

## The socket

This is the part worth being careful about.

The browser `WebSocket` constructor cannot set headers, so the credential has to
be something the browser attaches on its own: the session cookie. That works
here because the socket is same-origin (`/online/ws` on the app's own host), and
it is already how `stapes_uid` reaches the Worker today.

Two things make it not exploitable:

1. **A WebSocket handshake is not subject to CORS.** Any page anywhere can open
   a socket to our host. What it cannot do is get the *cookie* attached: Better
   Auth's session cookie is `SameSite=Lax`, and a handshake is not a top-level
   navigation, so browsers withhold it cross-site. The upgrade therefore arrives
   unauthenticated and is refused.
2. **An explicit `Origin` check**, because (1) is a browser behaving correctly
   and this costs one string comparison.

```ts
// workers/app.ts
if (url.pathname === GAME_SOCKET_PATH) {
  if (request.headers.get("Origin") !== url.origin) {
    return new Response("Bad origin", { status: 403 });
  }
  const session = await auth().api.getSession({ headers: request.headers });
  if (!session) return new Response("Sign in first", { status: 401 });

  const headers = new Headers(request.headers);
  headers.set(ACTOR_HEADER, session.user.id);
  return gameServer(env).fetch(
    new Request(url, { method: request.method, headers }),
  );
}
```

The verified id travels to the Durable Object in a header rather than the query
string it uses today — it stays out of request logs, and the object is only
reachable through the binding so nothing outside this handler can set it. The DO
reads that header and **400s when it is missing**, so a future caller that skips
the check fails closed instead of spawning an anonymous actor.

The DO itself gains no database access. Identity is settled before the socket
exists, which keeps D1 out of the tick loop entirely.

### What this does not do

**A revoked session does not close a live socket.** Logging out in one tab
leaves that tab's socket authenticated until it disconnects. Fix in this change:
`/logout` closes the socket client-side. Left undone: an admin banning somebody
mid-session does not eject them until they reconnect. Cheap to add later — the
DO already has a tick, so it could re-check on an alarm — but it is a database
read per player per interval, and not worth paying before there is a ban to
enforce.

### Why not a one-time token

Better Auth's `oneTimeToken` plugin is the standard answer when the socket is
cross-origin and cookies cannot ride. It is the wrong trade here: the socket is
same-origin, and `online.tsx` reconnects on a backoff up to ten seconds, so
every reconnect would need a fresh token fetch first — a round trip added to
exactly the moment the connection is already unhealthy. Worth revisiting only if
the game server ever moves to its own origin.

## Schema generation

`auth generate` has to import an auth config, and ours reads `env.DB`, which
does not exist outside the Worker. So `app/lib/db/auth.config.ts` exports a
module-level `auth` built from the same options over a throwaway Drizzle client.
It is never deployed; the CLI only needs the option shape to know what tables to
emit.

```
pnpm auth:schema     # auth generate --config app/lib/db/auth.config.ts --output app/lib/db/schema.ts
pnpm db:generate     # drizzle-kit generate  -> app/lib/db/migrations
pnpm db:migrate:local
pnpm db:migrate:remote
```

`auth:schema` is a one-off, re-run only when a plugin is added. Day to day this
is just drizzle-kit and wrangler, matching inploi-studio.

Both the Vite plugin and `wrangler d1 migrations apply --local` persist to
`.wrangler/state` from the repo root, so local dev and local migrations see the
same database without a `--persist-to` flag.

## Secrets

`BETTER_AUTH_SECRET` (from `auth secret`) and `ADMIN_EMAIL` go in `.dev.vars`
locally and `wrangler secret put` in production. **`.dev.vars` is not currently
in `.gitignore`** — add it in the first commit, before the file exists.

## Seeding the admin

The `databaseHooks` hook above makes whoever signs up with `ADMIN_EMAIL` an
admin. `scripts/seed-admin.ts` POSTs `/api/auth/sign-up/email` at a running dev
server with the local dev password, so a fresh clone gets an admin account in one
command.

**Production has an ordering hazard.** Email is not verified — there is no email
provider configured — so the hook alone means the first person to sign up as
`rincofrederico@gmail.com` becomes admin. The account must therefore be seeded
against production immediately after the first deploy, before the URL is shared;
after that the address is taken and sign-up rejects it. Once the row exists,
pinning `adminUserIds: [<that id>]` alongside the hook makes it belt and braces.

Two related gaps, both out of scope and both wanting an email provider (there is
a `cloudflare-email-service` skill for this): **no email verification** and **no
password reset**. A forgotten password today is a D1 row edit.

## Tests

`workers/` runs under `vitest-pool-workers` against the real `wrangler.jsonc`, so
the D1 binding appears in tests as soon as it is added — but empty. A setup file
applies migrations with `readD1Migrations` + `applyD1Migrations` from
`cloudflare:test`.

- `workers/app.test.ts` (new): upgrade with no cookie → 401; with a foreign
  `Origin` → 403; with a valid session → 101 and the DO sees the right id.
- `workers/GameServer.test.ts`: switch the handshake from `?actor=` to the
  header; add a case proving a header-less upgrade is refused.
- `app/lib/auth.test.ts`: the role hook — `ADMIN_EMAIL` gets `admin`, anything
  else gets `user`.

Per AGENTS.md, prove each test can fail before believing it.

## Order

1. D1 database, binding, `.gitignore`, secrets, migration scripts. Nothing wired.
2. Better Auth instance + schema + first migration. `/api/auth/*` mounted.
3. `/login`, `/signup`, `/logout`, root loader, role-aware `AppShell`.
4. Guards on the editor and `/play`. Seed script.
5. `/online` on sessions: drop `ACTOR_COOKIE`, socket guard, DO header. This is
   the one that changes the protocol, so it goes last and alone.
