# Deploy

- `DATA_DIR` must be mounted as a directory: the WAL and SHM files sit beside `stapes.db`, and Coolify's persistent storage fails on a single file (coolify#5337).
- The `Dockerfile` installs `curl` because Coolify's healthcheck runs inside the container with `curl` or `wget`, and the slim `oven/bun` image has neither. Without it every deploy is marked unhealthy and rolled back.
- `CMD` is exec form so Bun is PID 1 and receives `SIGTERM`. Through a shell, `World.drain` never runs and a deploy loses up to a checkpoint interval of play.
- `docker-compose.yml` sets `mem_limit` so a container that leaks dies inside its own cgroup rather than handing the choice to the OOM killer. It caps each container, not their sum, which is why previews run on their own box (`SETUP.md`, step 6).
- `deploy.yml` and `preview.yml` wait on Coolify's deployment record, not `/api/health`. Coolify's deploy API returns when the deploy is queued, and the old container answers `/api/health` until it is replaced.
- `deploy.yml` uploads the client, deploys the server, then activates the client. Activating first puts a client with a new `PROTOCOL_VERSION` in front of the old server, and every tab reloads into the same mismatch.
- `scripts/prune-preview-volumes.sh` deletes preview volumes because Coolify 4.3.10 does not when a PR closes. Its three guards (preview app UUID prefix, `-pr-N` suffix, dangling for over a day) keep it off production and backup volumes, which are briefly dangling during a normal deploy; Coolify's `delete_unused_volumes` would match them.
- `scripts/cap-previews.sh` stops all but the `MAX_PREVIEWS` most recently created preview containers, because the Coolify webhook starts a preview before `preview.yml` runs and the workflow cannot refuse one. The number is set twice, in the cron file on the preview box and in the repository variable `MAX_PREVIEWS` that `preview.yml` warns with, and the two are kept equal by hand.
- The landing page's canonical link and Open Graph tags name `https://thelaststones.com` (`CANONICAL_ORIGIN` in `app/components/home/content.ts`), and so does `/changelog`'s canonical link. Link-preview crawlers need an absolute image URL and `/` is prerendered at build time, so the origin is written into the page rather than read from the server's `PUBLIC_ORIGIN`. `itch/index.html` links to the same origin. Moving the domain means changing all three.
- `BOTS=n` makes the server start one bot process playing `n` bots in its own container (`server/bots.ts`), so they share the container's memory limit and stop when it stops. One bot is about 130 MB and ten about 650 MB. A server with players roaming measured 400–510 MB, so a preview with one bot needs `768m` rather than `512m`. Bots run just as well from another machine (`bun run bots --url`), which costs the server only their players. With `OPENAI_API_KEY` set on the server, it is passed to the bot process and the bots talk; without it they play silently.
- A bot started by the server reaches it on `127.0.0.1` but sends `PUBLIC_ORIGIN` as its `Origin`. Better Auth on a deployed server trusts only that origin (plus `BETTER_AUTH_TRUSTED_ORIGINS`), so a bot sending its localhost address is refused at sign-in.
- `itch/index.html` sends players to the game in a new tab instead of embedding it. itch serves an HTML upload from `html-classic.itch.zone` in a frame on `itch.io`, which is a cross-site context for the game, and the session cookie is `SameSite=Lax` (`server/auth.ts`), so the browser never sends it there and nobody could stay signed in. Uploading `build/client` fails before that: it loads `/assets`, `/api` and `/online/ws` from the root of whatever serves it, and itch serves an upload under `/html/<id>/`.
- The `itch` job in `deploy.yml` runs only after a production `deploy`, so the version it gives itch, the short commit, is always one that went live to players. A staging deploy skips it, because the page is public. `BUTLER_SHA256` is the checksum of broth's zip for `BUTLER_VERSION`, checked because the job hands `BUTLER_API_KEY` to that binary. Change them together, taking the new checksum from `curl -fsSL https://broth.itch.zone/butler/linux-amd64/<version>/archive/default | sha256sum`.
- `release.yml` opens the release PR with the workflow's `GITHUB_TOKEN`, and GitHub starts no workflow for events that token causes. The release PR therefore gets no CI run and no preview, and CI's `changeset` job skips `changeset-release/` branches for the same PR. The repository must allow GitHub Actions to create pull requests (Settings → Actions → General), or the release step fails.
- `CHANGELOG.md` is bundled into `/changelog` at build time, so the page shows the release it was built with. Its section titles (New, Fixes, Big changes) are renamed from changesets' semver headings twice, in `app/lib/changelog.ts` and in `release.yml`'s Discord step, and are kept equal by hand.
- `@changesets/cli` 3 needs Node 22.11 or later. `changesets/action` runs it with `node`, so `release.yml` installs Node; CI's own `changeset status` runs under `bun --bun` and needs none.
- `deploy.yml` reads `PUBLIC_ORIGIN`, `COOLIFY_APP_UUID`, `ORIGIN_IP` and `ADMIN_SECRET` from the GitHub environment it deploys to, `staging` on a push to `main` and `production` from `release.yml`. A copy of one of those names left at repository level is used whenever the environment lacks it, so a missing staging value deploys to production instead of failing.
- Staging and production are separate worlds with separate databases. `server/lock.ts` lets one process hold a database, so they cannot share one, and an account made on staging does not exist on production.
- `release.yml` has no concurrency group on purpose. Only the run for the release PR's merge commit has no pending changesets, so it is the only one that tags and deploys; a group would cancel it while queued behind two newer pushes, and the version would stay untagged.
- If a release tagged but did not deploy (a failed or cancelled production job), a re-run finds the tag and publishes nothing. Deploy it by hand: `gh workflow run deploy.yml --ref v<version> -f environment=production`. The same command with an older tag rolls production back.
- Production gets its pre-deploy snapshot only on a release now. Staging gets none; see the comment in `deploy.yml`.
