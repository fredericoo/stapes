# Server

- `LocalStore.deleteAll()` and its server counterpart clear buffered key/value writes only, not tables written with raw `sql.exec`. `resetWorld` in `GameServer` drops the `chat` table and empties the `death` table by name for that reason.
- `MIGRATIONS` in `server/db.ts` is applied by position: `schema_version` records how many entries have run, not which. An entry that has run anywhere, including a PR's preview (whose volume survives every push until the PR closes), is never edited; a change is appended as a new entry. An edited entry is skipped where it already ran, and the entries after it run against the old schema, which stops the server at boot.
- A renamed tile id goes in `TILE_ID_RENAMES` (`app/lib/tileRenames.ts`), and its migration is appended to `MIGRATIONS` with `renameTileIdsSql`. A prefix rename rewrites every id starting with `from`; mark it `exact` to rewrite only placements whose `tileId` is `from`, or renaming `grass` would take `grass-2` with it. Worlds keep tile ids in their stored JSON, and `restoredEquipment` drops an item whose tile the catalogue no longer has, so a rename without the migration deletes every copy players hold. `LocalStore.restore` applies the same table to a tab's world, which `MIGRATIONS` never reaches, and stores how many entries it has applied, since a rename that frees an id for a new tile is not safe to apply twice. Entries are never removed: an old tab or preview may still hold the old ids.
- `ClientBundle.stored()` (`server/clientBundle.ts`) orders build ids by write time. They are commit shas, so an alphabetical sort would make `collectGarbage` delete arbitrary builds, including one about to be activated.
- `serveClient` (`server/serveClient.ts`) passes a GET's `Range` header on to `ClientBundle.respond`, which answers it with `206` and those bytes. Apple requires a server of media for iOS to answer byte ranges, and Safari asks for video that way, so a route that stops passing the header on is expected to break playback on an iPhone and nowhere else a desktop test would show.
- `World.drain` (`server/world.ts`) closes every socket with code 1012 before exit, because Bun exits without sending close frames (oven-sh/bun#25722) and clients would otherwise wait for their own timeout.
- `World.drain` calls `GameServer.saveEveryActor` before `store.flush()`. `GameServer` puts actors and changed board chunks into the store only every `ACTOR_FLUSH_INTERVAL_MS` (30 s), so a flush alone commits a world up to that old. The sockets close after the database does, so the save a socket close makes is not written.
- On `SIGTERM` the server runs `World.drainAfterNotice`: with anybody connected it sends `serverRestarting` with `inMs`, keeps the world running for `RESTART_NOTICE_MS`, then drains. The default is 5000 when `NODE_ENV=production` and 0 otherwise, because `bun --watch` sends `SIGTERM` on every server edit.
- `POST /api/account` (`server/api.ts`) catches Better Auth's `APIError` and returns `status(400, …)`. `APIError.status` is a name such as `"UNPROCESSABLE_ENTITY"`, which Elysia cannot read, so uncaught it reaches the browser as a 200.
- `GameServer` reads the time only through its `now()`, which a world built with `manualTicks` advances one `TICK_MS` per `step()`. A `Date.now()` added to it puts that world back on wall time, and a stepped run stops repeating.
- `World.buildAuthoredMap` (`server/world.ts`) writes the built map before `GameServer.replaceWorld` runs, so a tree whose map cannot start a world (no `player` tile) leaves the new map stored and the old board playing; the record of what was built is written only after the replace succeeds, so the next start or save tries again.
- The map is built in a child process (`buildWorldMapApart` in `server/worldMap.ts`). The 4× showcase island's build peaks at about 1.8 GB on its own while the map it leaves is about 330 MB; built in the server's process, that garbage and the world it replaces would be in one heap. The parent reads the map back with `parseSharedMap`.
- Whether to build is decided by a hash of the tree, `tiles.json` and every non-test file under `app/editor`, `app/game` and `app/lib` (`builderSourceHash`), stored under `authoredMap` in the world's `kv`. Any code change there builds again, at about 25 s for the 4× island; whether to replace the board is decided by the hash of the map that comes out, so a build that changes nothing leaves the board, its creatures and dropped items as they were.
- `MIN_PASSWORD_LENGTH` (`app/lib/account.ts`) is a length floor only. An account's email is stored and nothing is sent to it, so there is no password reset.
- Every live entry of a live `WeakMap` adds to every collection's pause, eden ones included. A cache keyed by something the world holds one of per cell or per placement (a stack, a `PlacedTile`) ends up with hundreds of thousands of entries: `stackTexts` in `server/chunkJson.ts` held 266,000 after a minute with four players and made the median eden pause 24ms instead of 3. Key a cache by chunk or by tile def, or keep the value on something that already lives as long as it does. "Garbage collection pauses on the server, measured" in `docs/notes.md` has the measurements.
- A world being played holds one copy of each distinct stack that carries no nested data (`StackPool`, `app/lib/stackPool.ts`). `GameSession` builds its board with `shareMap`, and `GameServer` reads the map file with `parseSharedMap` and the checkpointed chunks through `shareCells`. Every cell with the same tiles holds the same frozen array of frozen placements, so a stack is changed only by replacing it through `setStacks` or `replaceStack`. A write into a stack or a placement in place throws; without the freeze it would change every cell sharing that stack. "Server memory: one copy of each distinct stack" in `docs/notes.md` has the measurements.

## Wire

- `parseServerMessage` uses valibot `v.object` schemas, which strip unknown fields. A field added to a message type but not to its schema is dropped in transit without a type error.
- `GameServer.seatJoiner` forgets the actor's step chain and step queue. A new socket is a new `RemoteSession`, which numbers its chains from 0, so a chain number kept from the displaced socket would refuse every step the new one sends. Nothing else may lower it: the world resets beside `queuedIntents.clear()` keep `stepChains`, because steps still on their way from a chain the server has just closed would be walked under a lower number.
- `GameServer.closeChain` adds one to the actor's chain rather than setting it to the refused step's chain plus one. A step refused for a full queue leaves the steps queued ahead of it, which belong to the chain it just closed; when one of those is refused later, the steps the client sent on its next chain are behind it, and a chain set from the refused step's number would let them through.
- `GameServer.flushCommandReplies` runs at the end of `tick`, after `broadcastPatch`. `RemoteSession.command` resolves when the reply arrives and its callers read the board straight after, so a reply sent from `webSocketMessage`, where the command runs, would reach them before the change it reports.
